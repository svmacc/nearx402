How one payment is decided two NEAR transactions, the rest is HTTP

HTTP1
402 from the vendor
Price, token and a nonce that lives five minutes.
local2
Agent proves
A Groth16 proof that the payment fits its cap, per-call limit and allowlist. About 200 ms, 256 bytes.
NEAR3
Contract verifies and pays
pay_zk: the proof is checked on chain, then the contract itself transfers the tokens and writes the log entry.
HTTP4
Agent retries with a receipt
Contract id, log number, nonce, transaction hash and a secret only the agent knows.
reads NEAR5
Facilitator checks
Code hash, log entry, token transfer event, nonce and receipt secret. It holds no key and sends nothing.
HTTP6
200, once
The same receipt again gets 402: already redeemed.
A blocked attempt stops at step 3: the proof fails, nothing moves, the attempt is logged.Five blocked attempts in one UTC day freeze the agent.

What this public page can and cannot see

Everything on this page is public chain data. Anyone could build it.

Public on NEAR

  • The recipient and amount of every payment. Token transfers are transparent.
  • The time and paying agent of each payment.
  • The recipient and amount of a rejected attempt, from its transaction arguments.
  • A daily total anyone can add up, which is a lower bound on the cap.

Not on chain

  • The daily cap and the per-call limit.
  • Allowed vendors that have not been paid yet.
  • Which rule a rejected attempt broke: the log says only "invalid proof".

The agent must hold the policy to prove it, so a compromised agent can read it, but it still cannot break it.

Try it three ways, none needs an account

1. Ask the contract, right here

A read-only call to the policy contract through the same public RPC this page uses. Nothing is signed, nothing is sent to the team.

Pick a method and press Query. The answer is the contract's raw JSON.

The same call from a terminal, or from an agent


        
The RPC returns result as the UTF-8 bytes of that JSON. Every method in the list is the contract's read API; the one write method an agent uses is pay_zk.

      

      

        
2. Run the whole flow on your machine

        
From a clone, with no accounts and no funds, scripts/demo-zk.sh starts a local NEAR sandbox and plays agent, vendor and attacker: one paid call, the replay rejected, two attacks blocked. It exits non-zero if any outcome differs from the README's table. With --network testnet it runs the same story against the contract above, using the agent key and the policy that the team holds; the recorded transactions below came from that.

        
3. Pay as the agent

        
Paying needs two things this page does not have: the agent's function-call key and the private policy values the proof is built from. Publishing them would publish the policy, the one thing this design keeps private. So on testnet the recorded transactions are the evidence, the sandbox demo makes you the agent on your own machine, and the owner account can register a further agent with its own policy for anyone who wants to run one against this contract.
